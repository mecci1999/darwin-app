# Trails synchronization architecture

## Trust and privacy boundary

- The service derives the actor and tenant exclusively from trusted `ctx.meta.user` and `ctx.meta.tenantId`. Request fields never select an owner or tenant.
- Capability roles are server-controlled, tenant/creator-space scoped data: `participant` is an ordinary authenticated user, `creator-space-owner` manages their own creator space, and `creator-space-editor` manages only its trusted assigned owner space. No action accepts a role, creator-space owner, user ID, or tenant ID from a client. Darwin `power === 999` remains a coarse platform-admin override, but is not the creator-role model.
- Every authenticated actor may use private field tools. Hikes, gear, packing plans, finance, and ShootSessions are always read/created in the trusted actor's own tenant/user scope; all private field records, including finance and ShootSessions, remain owner-only even for platform admins. Private field records never obtain public projections or generic cross-user sync access.
- Public photography content (portfolios, journals, categories, external videos, and comment moderation) plus guided-trip management require a creator-space owner/editor capability for the resource's tenant/space. `v1.capabilities` returns a typed server-derived UX snapshot; clients may use it to render controls, but each action remains authoritative.
- `deviceId` identifies a non-secret app installation for diagnostics. It is not an authentication, authorization, or permission credential.
- `v1.sync.pull` always filters every change to the current actor's `tenantId + userId`. The generic `owner` scope excludes `finance-entry`; `owner-finance` is an explicit owner-only scope for finance.
- The in-memory repository is a **development-only scaffold**. Its records, cursors, idempotency cache, and change log disappear on restart. A production repository must persist the resource write, version check, change event, and idempotency result transactionally.

## Durable Trails persistence configuration and v2 wire contract

`repository/mysqlPortfolioCategorySync.ts` implements an asynchronous MySQL adapter for the `portfolio-category` sync write/pull slice. It deliberately does **not** implement the synchronous `TrailsRepository` interface. The development-only `InMemoryTrailsRepository` remains available only to v1 actions; no v2 durable action falls back to it.

The adapter uses one managed transaction for every mutation lookup, locked current mutation/category read, owner-scoped slug check, CAS-protected resource write, owner-ordered `TrailsSyncChange` write, and `TrailsSyncMutation` result write. Its concrete Sequelize ports bind only `TrailsPortfolioCategory`, `TrailsSyncChange`, and `TrailsSyncMutation`; category updates use `tenant_id + id + resource_version` and reread the tenant-scoped row when the compare-and-swap update affects no row. Pull means `tenant_id + owner_user_id + cursor > after`, ordered by cursor ascending with a bounded limit; empty pages obtain the latest cursor in the same owner scope.

Database BIGINT resource versions and cursors stay decimal strings at the adapter boundary. Pull is limited to a configured safe page size (default 100, maximum 500), authorizes creator-space owners and scoped editors through the trusted actor helpers, and reads only the resolved owner scope. A duplicate mutation-key race rolls back its entire original attempt; the adapter then opens one bounded read-only replay transaction and returns only the exact stored fingerprint result. A different fingerprint is rejected and is never rerun.

`TRAILS_DURABLE_PERSISTENCE_ENABLED=true` explicitly enables the local MySQL-backed v2 composition slice. Only the exact lowercase value `true` enables it; all other values are disabled. `TRAILS_DURABLE_CATEGORY_SYNC` is a legacy fallback only when the new flag is absent. If both are present and their exact enabled values disagree, composition fails closed and remains disabled.

The lifecycle owns one private MySQL connection and composes the current durable category sync, portfolio, journal, hike, gear, packing plan, finance, media-commerce metadata, and media asset registry. Public category and catalog metadata may exist under their existing scoped public contracts. Public media delivery is intentionally deferred and unsupported: no resolver, delivery-base configuration, or public media catalog exists, and no public-media URL is emitted. Public portfolio output may expose only an opaque `coverMediaId`; it never resolves media metadata or projects a cover image, derivative, URL, dimension, locator, object key, or capability. It validates the trusted Photoshop ingestion-operation model set as part of the same schema contract, but does not compose an ingestion writer, private storage, COS client, preflight, CDN, public delivery capability, or any external effect. It never reads or writes `mainConnection`, `star.db`, or a global database singleton. Startup authenticates that private connection but never synchronizes schemas at runtime: migrations/schema must already be present before enabling v2. Startup failure and normal stop close the private connection and clear every composed state dependency; stop still clears state if close itself fails.

`v2.category-sync.push` and `v2.category-sync.pull` are category-only durable operations. They require trusted creator capability and use canonical decimal-string `baseVersion` and cursor values (`0` or a non-zero digit followed by digits); numeric JSON values and non-canonical strings are rejected. They never read from, write to, dual-write with, or fall back to `TrailsRepository`/the in-memory category list. Adapter unavailability and persistence failures are 503, while stale results remain HTTP 409.

## Vendor-disabled durable media commerce v2

`DurableMediaCommerceStore` is a separate MySQL v2 aggregate composed by the private durable Trails lifecycle. It never uses v1, the generic file domain, subscription/payment models, vendors, network calls, delivery URLs, credentials, provider identifiers, original files, object keys, bucket/path data, or signed URLs. `TrailsDurableMediaCommerce` contains typed commerce metadata in a private JSON payload with indexed tenant/owner/buyer/type/status columns; `TrailsDurableMediaCommerceMutation` stores trusted-actor mutation fingerprint/replay results. Every write takes a client mutation ID and a canonical decimal `expectedResourceVersion` (`null` for a creation), runs mutation replay/check, authoritative read, state validation, CAS, and result persistence in one managed transaction. Identical replay returns the stored result; altered reuse fails.

Media transitions are `draft → published → withdrawn`; print editions are `draft → sellable → withdrawn`; commercial inquiries are buyer-created `submitted` records; download requests are `requested → granted|declined` then `granted → revoked`; a grant creates an entitlement authorization record only and never a download capability. Orders snapshot the server-owned sellable edition title/currency/price in integer minor units. Manual states are facts, not proof: `submitted → payment-recorded|cancelled`, `payment-recorded → fulfilled|refunded`, and `fulfilled → refunded`; refunds are capped to the recorded payment. There is no checkout, payment collection, carrier action, shipment, email, tax, invoice, or external effect.

Public commerce resolves only the deployment-configured public owner and returns published media plus sellable editions whose media remains published. Its allowlist exposes only public metadata, eligible derivative references, and sellable pricing; derivative references are opaque metadata, not links. Buyer workspace is bound to the trusted actor and excludes owner identity, payment amount, delivery data, PII, and any URL. Owner workspace uses trusted creator-space controls. The model contains only authenticated buyer IDs and bounded inquiry content (no address, email, phone, payment instrument, or legal-contract claim); a future launch must add an independently reviewed buyer retention/disposal policy before collecting further PII. There is no reconstructive commerce audit payload.

The parallel `v2.categories.workspace`, `.create`, `.update`, `.archive`, `.reorder`, and `.public` actions are the bounded durable category-management milestone. They use only the same private MySQL category store: workspace and mutations require a trusted creator-space owner/editor, derive owner attribution through `creatorSpaceOwnerId`, and never accept caller tenant/owner fields. CRUD writes receive a server-generated mutation ID and write the category, an `upsert` sync change, and the durable mutation result in one transaction. Updates/archive/reorder require canonical decimal-string resource versions; reorder locks and verifies every active owner category before applying any change, so stale/ineligible inputs cannot partially apply. The public action reads only deterministic `sortOrder, slug` order and returns only `visibility=public`, `status=active` projections. It does not alter v1 category behavior or generic v1 sync.

Unit tests use transaction-capable fakes and concrete adapter seams only; they make no database connection. The separately named MySQL integration harness is skipped by default and runs only when `TRAILS_MYSQL_INTEGRATION=1`; its Compose target is disposable and the test refuses schema setup unless the connection database name is exactly `darwin_trails_it`. It applies only the existing category migrations directly, without Sequelize synchronization or production migration-runner ledger/locking state.

## Pull protocol

`v1.sync.pull` accepts an optional decimal non-negative cursor and an optional scope. Omitted cursors begin at the retained feed start, and omitted scope means `owner`.

1. A client sends its last successfully applied `nextCursor`.
2. The service returns only later changes permitted to the trusted current actor, ordered by ascending cursor, plus a new `nextCursor`.
3. The client applies the complete page durably before storing `nextCursor`; it must retain a local pending mutation rather than silently overwrite it with a pulled change.
4. Finance never appears in the generic feed. A finance pull requires the explicit `owner-finance` scope and remains restricted to the current owner.

Cursor values are opaque protocol tokens to clients even though the development repository currently formats them as integers. A future durable implementation may expire old cursors and require a documented full owner-scoped resync.

## Push protocol and conflicts

`v1.sync.push` requires a stable body `mutationId`, diagnostic `deviceId`, `resourceId`, and `baseVersion`. Retries must reuse the original body `mutationId`. The current JSON API does not require or enforce an `Idempotency-Key` request header. The repository keys idempotency by trusted tenant, trusted authenticated actor, and `mutationId`; it rejects a reused ID whose mutation contents differ.

For an existing resource, `baseVersion` must equal the authoritative `resourceVersion`. If another device wrote first, the service responds with HTTP 409 and a structured `STALE_VERSION` result containing the authoritative resource and version. Clients must preserve their local candidate and require an explicit user decision; they must never retry by silently replacing the server resource. New resources use `baseVersion: null`.

The current development write capability is intentionally limited to typed `portfolio-category` upserts. Pull may return all permitted resource types, but broad resource push requires per-resource field validation and business rules before it can be enabled. Server-controlled ownership, timestamps, lifecycle, status, and resource version are never accepted from a push payload.

## Future invalidation

Synchronization remains cursor reconciliation. A future WebSocket or platform push notification may only signal that a device should perform a normal pull; it must not contain private resource data, advance a cursor, authorize a request, or replace the pull protocol. Device registration and device permissions are intentionally out of scope.

## Photography technical metadata foundation

## Authenticated route and equipment sharing

Routes, equipment specifications, and packing recommendations may be shared only through an explicit `TrailsShareGrant` to a specified authenticated user in the same trusted tenant. Grant creation requires a deployment-injected trusted Darwin recipient directory and fails closed when it is unavailable; request parameters never establish recipient tenancy or membership. This is not `visibility`, a public endpoint, or a sync scope. Recipient reads use allowlist-only projections: hikes provide a title, date-level occurrence, route label, distance, and elevation only; gear provides a display name, weight, and quantity; plans provide a name, snapshot weight, and nested projected gear entries. The service never shares private geometry, route provider IDs, exact timestamps, internal inventory IDs, owner/tenant/audit fields, finance, receipts, or any `ShootSession` content. Grants can expire and owners can revoke them; revoked or expired grants produce no recipient projection.

## Photography weather boundary

`v1.weather.forecast` is an authenticated, actor-scoped private field tool. It is disabled unless the deployment composition root injects a reviewed `WeatherService`; no provider URL, API key, request, or fallback exists in the default service. `CachedWeatherService` rounds input coordinates to 0.01 degrees before dispatch, isolates cached responses by trusted tenant and user, bounds and prunes its process-local cache, and returns only the rounded dispatch location together with deployment-bound provider/source metadata, fetched timestamp, provider validity timestamp, and fresh/cached status. Weather output is neither a public projection nor a `ShootSession` field, and it must not be used to infer an exact location.

Before enabling a provider, production must separately review provider terms, attribution, quota, location-data processing, timeouts, circuit breaking, observability, cache policy, and the photography-specific field mapping for cloud, precipitation, wind, visibility, sun, and moon. Windy access, if chosen, is a separately credentialed and policy-reviewed integration; a subscription alone is not an API authorization.

## COS connectivity verification boundary

`cos-verification.ts` is an unregistered server-only operational module, independent of `src/core/file`, Trails media, and durable commerce. It is disabled unless `TRAILS_COS_ENABLED` is exactly `true`; it accepts no client input and has no Trails action. With valid local/development static-environment credentials, it performs only `headObject` against one compile-time fixed bucket, region, and verification key under `masters-private/cos-validation/`; an operator cannot configure that target. It never lists, uploads, downloads, deletes, signs, exposes, logs, or returns COS bucket/object/header/credential/provider details. Its response is limited to redacted availability and normalized reason codes. Static credentials are deliberately unsupported in production until a separately reviewed server identity provider exists.

The public derivative foundation keeps COS masters and all codec-specific derivatives private. A server-only publication worker may approve a complete persisted 3×3 private artifact matrix under `workload-identity`; the registry then deterministically derives immutable opaque references from the approved JPEG metadata and never stores or returns a COS key, URL, locator, bucket, or credential. No action can submit a public reference. `TRAILS_MEDIA_PUBLICATION_ENABLED` is `false` by default. In production, startup rejects enabled legacy COS seams, every local provider/credential/token/mapping-secret setting, public delivery bases, and any partial delivery configuration. Enabling the foundation requires only the validated non-secret CDN distribution, COS bucket/region, immutable public-derivative namespace identifiers, and the exact `workload-identity` mode; it does not compose a worker, publish an object, or grant browser/cloud credentials. CDN configuration must use private COS origin access restricted to the immutable approved namespace; no bucket public ACL is part of this design.

`cos-ingestion-versioning-preflight.ts` is a separate, unregistered server-only readiness boundary; it does not compose with the connectivity verifier or any ingestion storage adapter. It is disabled unless `TRAILS_COS_INGESTION_VERSIONING_PREFLIGHT_ENABLED` is exactly `true`, allows only development/test local credentials, reads no mapping secret, and exposes no action. Its narrow client makes only fixed-scope `getBucketVersioning` calls. It never constructs a writer or changes versioning, ACLs, bucket configuration, objects, lifecycle, or runtime feature registration. Its safe result accepts the explicit `NoSuchVersioningConfiguration`, `Enabled`, and `Suspended` states because private keys are fence-token-derived and immutable; malformed/unknown responses and all other errors fail closed. It remains disabled in production.

`Portfolio.photoTechnicalMetadata` is an owner-private annotation attached to one work item. It contains normalized capture settings, an optional calibrated *label* (never GPS coordinates), controlled technical/process tag identifiers, bounded owner custom labels, a bounded plain-text creation note, and opt-in grouped visibility. Labels are identifiers rather than UI copy so clients can localize/present the controlled taxonomy without embedding UI labels in the service business rules.

`v1.portfolio.metadata.workspace` and `v1.portfolio.metadata.update` require trusted `ctx.meta` and same-tenant owner/admin authorization. The public portfolio action first requires the parent portfolio to be both `visibility=public` and `lifecycle=published`, then returns only metadata groups enabled by the owner. It never returns raw EXIF payloads, GPS coordinates, private original capability references, object keys, or original URLs. Metadata validation accepts bounded plain text only (no HTML), positive bounded numeric values, an ISO date, an accepted shutter representation (`1/125` or `0.5s`), and fixed controlled tag IDs.

There is deliberately no EXIF parser, upload integration, cloud source, or client-provided EXIF ingestion action. A future extractor may produce the typed `PhotoTechnicalMetadataPrefill` only from a server-controlled source; the owner still chooses visibility and annotations. The current in-memory record remains development-only. Production requires a migration plus transactional persistence, authorization/audit coverage, and a reviewed server-side metadata extraction pipeline before importing any file metadata.

## Guided photography trips foundation

The development-only repository now contains a deliberately narrow guided-trip foundation. `GuidedTripPlan` is tenant/owner scoped and separates public-safe itinerary, capacity, checklist, public material references, plan lifecycle (`draft`, `open`, `closed`, `cancelled`, `completed`) and weather/cancellation state from owner-only operational notes. Public actions (`v1.trips.public`, `v1.trips.public-detail`) enforce `visibility=public`, `lifecycle=published`, and non-draft trip status, then return an explicit projection that contains no owner identity, private notes, participant data, exact meeting information, payment or operational details.

`GuidedTripRegistration` is private and binds `participantUserId` exclusively from trusted `ctx.meta`; request data cannot register or overwrite another user. It allows only a contact-preference placeholder plus required acknowledgement/release acceptance timestamp and version. It intentionally does **not** collect medical, emergency-contact, payment, insurance, identity-document, or signature data. Explicit statuses are `submitted`, `waitlisted`, `approved-awaiting-payment`, `confirmed`, `rejected`, and `cancelled`. Full capacity sends new applications to `waitlisted`; owner/admin promotion to either capacity-reserving state is rejected if it would overbook.

Owner plan/status/contingency and registration transition actions require `actorCanManage`: same-tenant owner or platform admin. Plan transitions are `draft → open/cancelled`, `open → closed/cancelled/completed`, and `closed → open/cancelled/completed`; `cancelled` and `completed` are terminal. Once a plan is terminal, `v1.trips.registration-status` rejects every registration transition, including cancellation, so no existing registration can be promoted or otherwise silently mutated. A cancelled contingency makes the plan cancelled and non-public, and registration rejects it even for inconsistent legacy data. Participant reads are restricted to the trusted current participant. `v1.trips.owner-summary` is owner/admin-only and reports counts and safe capacity totals; it is not a public roster endpoint. Trips are intentionally excluded from the generic development sync feed until durable persistence, transition auditing, and a dedicated sync policy exist.

This foundation does not integrate payment, refunds, insurance verification, contracts, e-signatures, booking, notifications, real uploads, or operator compliance. Before any public trip launch, use the project launch-gate evidence register and obtain jurisdiction-specific professional legal, insurance, permit, safety, consumer-policy, privacy/retention, and operator review. Production also requires a transactional persistent repository, migrations, backups/restores, authorization and privacy regression tests, audit logs, and incident/weather operations.

## Approval-first publishing package foundation

`PublishingPackage` is a creator-space-internal, development-only metadata record attached only to a portfolio that is already `visibility=public` and `lifecycle=published`. Creator-space owners and trusted scoped editors may create/list/manage records using the existing `creatorSpaceOwnerId` and `actorCanManageCreatorSpace` helpers; participants and client-provided role, owner, or tenant fields do not grant access. Packages are intentionally excluded from broad sync until a durable audit policy exists, have no public projection, and store no platform credential, token, cookie, session, post identifier, or media object reference.

The explicit lifecycle is `draft → prepared → reviewed → approved → ready_manual_publish/scheduled → published → measured → learned`. `scheduled` records a human manual-handoff intent only; it creates no timer, background task, platform schedule, or post. `published` requires an explicit human manual-confirmation and records no platform API request. Xiaohongshu is always `manual_handoff`. Instagram may be labelled `official_api_candidate`, but that path is blocked from ready/scheduled/published until a separately reviewed future OAuth and platform-policy capability exists.

The package stores bounded copy, content origin (`human` or `ai-draft-requires-review`), and crop/export **intent metadata only**. There is no AI model/provider call, crop operation, storage export, upload, scraping, or browser automation. Approval requires all five human checks: copy, media selection, rights, location privacy, and factual claims. It is blocked when a withheld location includes GPS/route hints, restricted rights lack a disclosure, or any factual claim remains unverified. Measurement is manually entered after manual publication and learning conclusions must carry `low`, `medium`, or `high` confidence.

Attribution uses only a configured exact HTTPS destination origin and emits `utm_source=instagram|xiaohongshu` plus `utm_medium=social`. Credentials, non-HTTPS URLs, unconfigured origins, redirect endpoints, and redirect-shaped query parameters are rejected so the generator cannot become an open redirect.
